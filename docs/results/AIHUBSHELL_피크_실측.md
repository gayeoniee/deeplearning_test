# aihubshell 이 받는 도중 디스크를 얼마나 쓰나 — 소스를 읽은 값

**2026-08-26** · 방법: `uv run python tools/crops.py --shell-peek`
· 대상: `aihubshell` 7,824 bytes / 232줄 (AI Hub 가 배포하는 셸 스크립트)

추정이 아닙니다. **스크립트를 읽었습니다.** 80GB 를 도박으로 받아보며 재는 것보다
공짜이고 확실해서 이 방법을 골랐습니다.

## 왜 쟀나

`tools/crops.py --plan` 이 "필요 — 보수 = zip × 2" 를 필요량으로 내걸어 TL02 를
불가능으로 찍고 있었는데, **그 2배의 근거가 틀렸습니다.** `src/aihub.py:498` 의
경고를 옮긴 것이었고 그 경고는 *"zip 을 받은 뒤 **압축을 풀므로**"* 라는 이유로
붙은 값입니다. 우리는 `--mode zip` 으로 **압축을 안 풉니다**.

그래서 근거를 다시 찾았고, 진짜 이유는 다른 데 있었습니다.

## 읽은 것

| 줄 | 하는 일 | 그 순간 디스크에 사는 것 |
|---|---|---|
| 111 | `curl -L -C - -o "download.tar" …` | `download.tar` — **1배** |
| 124 | `tar -xvf download.tar` | tar + 풀린 내용 — **2배** |
| 139 | `find … -print0 \| sort -zt'.' -k2V \| xargs -0 cat > "${prefix}"` | tar + 조각 + 합친 파일 — **3배** |
| 142 | `rm "${prefix}".part*` | 조각 삭제 — 합친 **다음**이라 최대치는 안 줄어듦 |

세 가지가 이 판정의 근거입니다:

1. **`tar -xvf` 뒤에 `download.tar` 를 지우는 줄이 없습니다.** 스크립트 안의
   `rm … .tar` 은 줄 100 — 다운로드(111)보다 **앞**이라 이전 찌꺼기 청소입니다.
   `prepare_local.py` 가 `aihub.cleanup_backups(raw)` 로 치우긴 하는데
   다운로드가 **끝난 뒤**라 최대치는 그대로입니다.
2. **병합이 덮어쓰기(`cat … >`)입니다.** 조각과 합친 파일이 같이 삽니다.
   ⚠️ 줄 138 에 `#cat "${prefix}".part* > "${prefix}"` 가 있는데 **주석**입니다.
   진짜 병합은 139 줄의 `find | sort | xargs cat >` 이고, 방향은 같습니다.
   (처음에 정규식으로 6줄만 뽑았다가 이 줄이 잘려서 판정을 못 했습니다 —
   셸 스크립트는 덩어리째 봐야 합니다)
3. **조각 삭제는 병합 뒤**(142)라 겹치는 구간을 못 줄입니다.

## 결론

**받는 도중 최대치 = 청크 내용물의 2~3배.**
조각(`.part*`)으로 안 쪼개진 청크면 ② 에서 끝나 2배입니다. 쪼개졌는지는
받아보기 전엔 모릅니다 — 그래서 범위로 적습니다.

| 청크 | 크롭 끝난 뒤 | **받는 도중 최대치** |
|---|---|---|
| VL01 21GB | 21 + 2.6 = 23.6GB | **42 ~ 63GB** |
| TL02 80GB | 80 + 9.9 = 89.9GB | **170 ~ 250GB** |

## 이 PC(가연 작업 PC, 전체 237.8GB) 에서의 판정

TL02 는 **불가능합니다.** 다 비워도 93.3GB 이고, 최대치 250GB 는
**디스크 전체 용량보다 큽니다.** 여유의 문제가 아니라 물리적으로 안 됩니다.

→ 다른 드라이브(`DOG_SKIN_DATA`) 나 다른 PC (`docs/OTHER_PC.md`).
   그 PC 에 필요한 여유는 90GB 가 아니라 **250GB** 입니다.

## 안 재본 것

- 조각이 실제로 몇 개로 쪼개지는지 (2배냐 3배냐를 가릅니다)
- 실제 최대치를 초 단위로 샘플링한 값 — 소스만 읽었지 관측은 안 했습니다.
  다음에 청크를 받을 일이 있으면 그때 재서 이 문서를 갱신하세요.
