## 우리는 이미 파인튜닝 중이었습니다 — 다만 백본이 거의 안 움직였습니다

용어 정리:

```
전이학습 (transfer learning)   ← 우산 개념
  ├─ linear probe   백본 얼리고 헤드만
  └─ fine-tuning    백본까지 같이       ← 처음부터 이쪽
```

`freeze_backbone()` 은 정의만 되어 있고 **어디서도 호출하지 않습니다.**
백본은 계속 학습됐습니다. 문제는 **속도**입니다:

```
헤드 lr = 3e-4
백본 lr = 3e-4 × 0.1 = 3e-5     ← 12 에폭 ≈ 11,800 스텝 동안 거의 제자리
```

`backbone_lr_mult=0.1` 은 "ImageNet 특징이 이미 쓸 만하다" 는 전제인데,
ImageNet 은 **물체**를 구분하도록 배웠고 우리 과제는 **피부 질감·색의 미세한 차이**
입니다. 도메인 격차가 커서 백본이 적응할 시간이 필요합니다.

→ `config.FT_PRESETS` 로 강도를 바꿔 실험합니다 (노트북 03 의 7번).
   `conservative`(0.1, 현재) / **`moderate`(0.3, 1순위)** / `aggressive`(1.0) /
   `linear_probe`(0, 대조군).

## 2차 실행 — 1단계만 (2026-08, `moderate` 파인튜닝 / 12 에폭)

| 항목 | 1차 (bb×0.1, 8ep) | 2차 (bb×0.3, 12ep) | 차이 |
|---|---:|---:|---:|
| AUROC | 0.8031 | **0.8100** | +0.0069 |
| recall 0.95 지점 precision | 0.640 | 0.649 | +0.009 |
| 임계값 | 0.3057 | 0.2822 | — |
| best 에폭 | 5~6 | **6** | — |
| 소요 | 57.3분 | 87.4분 | +30분 |

### 읽는 법: 파인튜닝 강도는 1단계의 병목이 아니었습니다

+0.0069 는 검증셋 7,751장에서 **부트스트랩 오차 범위(±0.01 수준) 안**입니다.
"백본을 3배 세게 움직였더니 좋아졌다"고 말할 수 없습니다.

학습 곡선이 그 이유를 보여줍니다:

```
[ 5] train 0.5505 | val 0.5628 | macroF1 0.7286  ★ best
[ 6] train 0.5422 | val 0.5645 | macroF1 0.7286  ★ best   ← 여기가 최고
[ 7] train 0.5312 | val 0.5666 | macroF1 0.7238           ← val loss 상승 시작
[11] train 0.5133 | val 0.5723 | macroF1 0.7246
조기 종료 — 5 에폭 동안 개선 없음
```

- val loss 가 epoch 5 에서 바닥, 이후 계속 상승 → **수렴 후 과적합 진입**
- 2단계와 정반대입니다 (2단계는 12에폭 전부 best 갱신 = 과소적합)
- 즉 **1단계는 이 설정에서 이미 한계**입니다. 에폭을 늘려도 안 됩니다.

### 1단계의 실제 병목은 해상도로 보입니다

`full` 크롭은 1920×1080 의 중앙 정사각(1080×1080)을 잘라 224px 로 줄입니다.
병변 면적은 원본의 0.47%(A1) ~ 3.08%(A6) 이므로, 224px 입력에서 병변은
**대략 20~40 픽셀**입니다. ResNet50 의 마지막 특징맵은 224 입력에서 7×7
(격자 한 칸이 32px) 이라, 작은 병변은 **격자 한 칸 안에 갇힙니다.**

→ 다음에 시도할 것: **1단계 입력 384px**. 병변이 ~35~70px 이 되고 특징맵은 12×12.
   크롭은 디스크에 512px 로 저장돼 있으니 업스케일 없이 384 까지 갑니다.
   비용은 (384/224)² = 2.9배 계산이지만, **GPU 가 병목이 아니라면 벽시계
   시간은 그만큼 안 늘어납니다.** 그래서 `bench.report` 를 먼저 돌립니다.

### 바로 적용할 것: patience

best 가 epoch 6 인데 patience=5 라 11까지 돌아 **43분을 더 썼습니다.**
1단계는 5~6 에폭에서 수렴하는 게 두 번 확인됐으므로 `early_stop_patience=3`
으로 낮추면 다음 실행에서 ~30분을 아낍니다. (2단계는 아직 수렴 전이라 그대로)

## 8-C 배율 증강 실험 — 결론 없음, 대신 **왜 안 되는지**를 찾았습니다

| 조건 | `default` | `scale_robust` |
|---|---:|---:|
| 0.5x (축소) | 0.3346 (**−33.2%**) | 0.3325 (**−31.6%**) |
| 0.71x (축소) | 0.4311 (−14.0%) | 0.4008 (−17.5%) |
| **1x (원본)** | **0.5011** | **0.4858** |
| 1.41x (확대) | 0.4917 (−1.9%) | 0.4874 (+0.3%) |
| 2x (확대) | 0.4503 (−10.1%) | 0.4624 (−4.8%) |
| **최종 하락** | **33.2%** | **31.6%** |

33.2% → 31.6% 는 잡음입니다 (같은 설정 재실행에서 30.7% ↔ 27.8% 로 흔들립니다).
**증강은 효과가 없었습니다.**

### 하지만 표의 모양이 이유를 말해줍니다

**축소(0.5x)에서만 무너지고 확대는 멀쩡합니다.** 그리고 `scale_robust` 가 개선한 건
정확히 확대 쪽뿐입니다 (2x: −10.1% → −4.8%).

원인: **`RandomResizedCrop` 은 축소를 못 합니다.**
이미지의 일부를 잘라 목표 크기로 **확대**할 뿐이라, 가장 축소된 경우가
"이미지 전체" 입니다. `rrc_scale` 하한을 낮추면 **확대 쪽만** 넓어집니다.

실측 (512px 크롭 → 224px 입력, 검증 변환 대비 상대 배율):

| 프리셋 | 훈련에서 보는 배율 | 0.71x 이하 | 0.5x 이하 |
|---|---|---:|---:|
| `default` (0.70,1.0) | 0.69x ~ 1.04x | 2.2% | 0.2% |
| `scale_robust` (0.35,1.0) | 0.80x ~ 1.45x | 1.7% | 0.5% |
| **`zoom_both`** (+affine 0.45~1.25) | **0.43x ~ 1.38x** | **32.0%** | **7.4%** |

**훈련에서 한 번도 안 본 구간(0.5x)을 시험하고 있었습니다.**
증강을 아무리 세게 해도 그 방향으로는 안 넓어지니 하락이 안 줄어든 게 당연합니다.

### 고친 것

- `CFG.affine_scale` + `T.RandomAffine(scale=...)` — 이미지를 **실제로 줄이고 여백을 채웁니다**
- 새 프리셋 `zoom_both`: `rrc_scale=(0.5,1.0)` + `affine_scale=(0.45,1.25)`
- `scale_robust` 는 남겨두되 "확대 전용" 이라고 명시

### 1차 실험의 또 다른 결함

8-C 가 `with_finetune` 을 안 걸어 백본 lr 이 `conservative`(×0.1) 였습니다.
그래서 원본 macro-F1 이 0.5011 로, 4번의 0.548(=`moderate`)과 비교가 안 됩니다.
또 `scale_robust` 는 **25에폭 전부 best 갱신**(마지막 0.4995)이라 아직 덜 학습됐습니다 —
증강이 세지면 더 오래 걸립니다.

→ 재실험은 `with_finetune("moderate")` + **35에폭** + 표본 3,000장으로 맞췄습니다.

### 판정 기준 (재실험 전에 정해둡니다)

| `zoom_both` 하락폭 | 판정 |
|---|---|
| ≤ 15% | ✅ 통함. 기본 증강으로 채택 → 04 진행 |
| 15~25% | 🤔 애매. 검증 점수 손실이 작으면 채택 |
| ≥ 25% | ❌ 증강으로 안 잡힘 → 고정 픽셀 크롭(f320) 또는 다중 스케일 학습 |

⚠️ 실행 간 잡음이 ±3%p 입니다. 검증 macro-F1 이 조금 내려가도
**하락폭이 크게 줄면 배포에는 그쪽이 낫습니다.**

## 8-C 재실험 결과 (2026-08-21) — ❌ 증강으로는 안 잡힙니다

VL01 / ResNet50 / 224px / `with_finetune("moderate")` / 35epoch / 배율 교란 표본 3,000장.

| 프리셋 | 원본 macro-F1 | 최악 조건 | 하락 |
|---|---:|---:|---:|
| `default` | 0.5471 | 0.3928 | **28.2%** |
| `zoom_both` | 0.5348 | 0.3866 | **27.7%** |

**판정: ❌** (사전에 정해둔 기준의 "≥ 25%" 구간)

- 0.5%p 차이는 실행 간 잡음(±3%p) 안입니다. **차이가 없다**고 읽어야 합니다.
- 검증 점수는 오히려 0.012 내려갔습니다. 축소 증강은 정보를 지우기만 하고
  불변성은 못 줬습니다 — 대가만 치르고 얻은 게 없습니다.

### 이게 왜 중요한가

배율 문제를 입력 증강으로 잡으려는 시도는 이걸로 **두 번 실패**했습니다.

| 시도 | 하락 |
|---|---:|
| `scale_robust` (확대 전용) | 31.6% |
| `zoom_both` (축소 포함, 0.5x 이하를 7.4% 봄) | 27.7% |

두 번째 시도는 "훈련이 그 배율을 한 번도 안 봤다" 는 진단을 실제로 고쳤는데도
결과가 안 바뀌었습니다. 즉 **원인은 훈련 분포가 아닙니다.**

가장 그럴듯한 남은 설명: 512px 크롭을 224px 로 줄이면 병변의 질감
(비듬 알갱이, 농포 경계, 각질 결)이 **물리적으로 사라집니다.** 0.5x 로 더 줄이면
남는 게 색과 큰 얼룩뿐이고, 그건 A1~A6 를 가르는 정보가 아닙니다.
증강은 없는 픽셀을 되살려주지 못합니다.

### 다음 수단 — 배율을 가르치지 말고 없앤다

`f320`: 병변 중심에서 **항상 320px 정사각**을 잘라냅니다 (`crop.fixed_box`).
병변이 크든 작든 입력에서 차지하는 픽셀 수가 같아지므로, 배율이라는 축 자체가
사라집니다. 동시에 `m1.5`(면적 비례 크롭)가 흘리던 "박스 크기 = 정답" 지름길도 막힙니다.

```bash
py prepare_local.py --chunk VL01 --margins -320
```

만든 뒤 노트북 03 의 **8-B (크롭 방식 비교)** 로 `full` / `m1.5` / `f320` 을 붙여 봅니다.
판정은 검증 점수가 아니라 **배율 하락폭**으로 합니다 — 여기서도 25% 이상이면
입력 해상도(224 → 384)로 올라가야 한다는 뜻입니다.

⚠️ 04(백본 비교)는 계속 보류합니다. 배율 하락 28% 는 백본을 바꿔서 줄어드는
종류의 문제가 아니고, 지금 04 를 돌리면 무너지는 기준 위에서 6개 모델을 비교하게 됩니다.
