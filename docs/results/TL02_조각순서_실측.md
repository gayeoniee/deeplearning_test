# aihubshell 이 붙인 zip 이 열리지 않았습니다 — 조각 순서

**2026-08-27** · 맥북 (macOS, Apple Silicon) · TL02.zip 80GB
· 도구: `tools/fix_split_zip.py`

## 증상

`prepare_local.py --chunk TL02` 가 다운로드를 마치고 매니페스트 단계에서 죽었습니다.

```
zipfile.BadZipFile: File is not a zip file
```

그런데:

| 확인 | 결과 |
|---|---|
| 다운로드 로그 | `병합이 완료 되었습니다` · `✓ 확보 — 80.1GB` |
| `file TL02.zip` | `Zip archive data, at least v2.0 to extract, compression method=store` |
| 크기 | 86,016,937,297 bytes = 80.11 GiB (AI Hub 표기 "80 GB" 와 부합) |
| 조각(`.part*`) 잔여 | 없음 (aihubshell 이 병합 후 지웠습니다) |

**잘린 게 아니었습니다.**

## 원인

zip 의 목차(central directory)는 파일 **맨 뒤**에 있어야 합니다. `file` 은 앞
몇 바이트만 보므로 앞머리가 멀쩡하면 "Zip archive data" 라고 합니다.
파이썬은 뒤를 보므로 죽습니다.

목차를 찾아보니 **파일 끝에서 1 GiB 앞**에 있었습니다.

```
파일 전체        86,016,937,297
EOCD             84,943,195,451   (+22 = 84,943,195,473 에서 zip 이 끝남)
뒤에 남은 것      1,073,741,824   = 정확히 1 GiB
```

`aihubshell` 232줄 스크립트의 139줄:

```bash
find … -print0 | sort -zt'.' -k2V | xargs -0 cat > "${prefix}"
```

`-V` 는 "part2 < part10" 으로 읽는 **버전 정렬**입니다. 맥의 BSD `sort` 에서
이게 안 먹어 **문자열 순서**로 떨어졌습니다:

```
part0, part1, part10, part11 … part19, part2, part20 … part8, part80, part9
```

조각 81개 = 1 GiB × 80 + 117,591,377 bytes. 그중 **79개**가 제자리가 아니었습니다.

## ⚠️ 여기서 한 번 틀렸습니다 — 그게 이 문서의 요점입니다

처음엔 **"마지막 두 조각만 뒤바뀌었다"** 로 봤습니다. 근거는 두 숫자가
일치한다는 것이었습니다:

| | |
|---|---|
| 파일 끝 − zip 끝 | 1,073,741,824 |
| 목차가 있어야 할 곳 − 실제 있는 곳 | 1,073,741,824 |

**이 검산은 틀린 가설도 통과시킵니다.** 두 가설을 같은 목차 위치에 적용하면:

| 가설 | 목차 위치 | 앞쪽 항목 @2,909,712,736 |
|---|---|---|
| 뒤 1조각만 밀림 (**틀림**) | 84,890,793,488 ✅ | 2,909,712,736 |
| 문자열 순서 (**맞음**) | 84,890,793,488 ✅ | 24,384,549,216 |

목차에서는 같은 답, 앞쪽 항목에서는 다른 답. 실제로 돌려보니 틀린 가설은
항목 검증에서 **1/24** 로 걸렸습니다. 자리 계산만 믿었으면 80GB 를
잘못 덮어썼습니다.

실행 로그에서도 같은 일이 세 번 더 있었습니다 — `뒤 8조각`·`뒤 4조각`·`뒤 2조각`
가설이 **목차 355,212항목을 끝까지 읽어내고도** 항목 검증에서 2/40 이었습니다.

→ **관문을 셋으로.** ① 목차 시작 표시 ② 목차가 끝까지 읽힘 ③ 항목 40개의
로컬 헤더와 **파일 이름** 일치. 셋 다 통과한 가설만 씁니다.

## 남기는 교훈

* `aihubshell` 이 "병합이 완료" 를 찍어도 **믿을 수 없습니다.** 정렬 실패를
  스스로 알아채지 못합니다
* `file(1)` 로 zip 을 검사하면 안 됩니다 — 앞머리만 봅니다
* 이건 맥에서만 나는 문제일 수 있습니다. 윈도우(Git bash)에서 받은 VL01 은
  멀쩡했습니다. 다음에 다른 청크를 다른 PC 에서 받으면 **크롭 전에**
  `python -c "import zipfile; zipfile.ZipFile(경로)"` 로 한 번 열어보세요
* 복구 가설은 **싸고 그럴듯한 검산으로 고르면 안 됩니다.** 틀린 가설이
  그 검산을 통과합니다

## 안 재본 것

- 조각 이름이 실제로 `part0…part80` 이었는지 (병합 후 지워져서 못 봤습니다).
  `0번부터` 가 맞았다는 것만 압니다
- 맥 `sort` 의 어느 판이 `-V` 를 어떻게 처리하는지. `-z` 는 됐습니다
