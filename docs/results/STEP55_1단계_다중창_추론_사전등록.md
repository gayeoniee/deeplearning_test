# STEP 55 — 1단계에 320px 창을 여러 개 (추론만, 재학습 0) · 사전등록 (2026-09-13 오전, 결과 전)

> 돌리기 전에 씁니다. 로컬 · 같은 표본(STEP 50~54) · 작업 규칙 7(보호자 조건).

## 왜

사용자 관찰(2026-09-13): *"앱에서 같은 사진인데 네모 위치에 따라 결과가 다 다르다."* 맞습니다 — 1단계 `f320` 은 네모 **중심** 320px 창
하나만 보므로 네모가 병변에서 벗어나면 병변을 못 봅니다(프록시: 라벨 중심 recall 86.8% → 사용자 중심 72.9% → 화면 중앙 63.3%).
네모 의존을 없애는 시도(틀 제거 STEP 43 · 검출기 STEP 50~52)는 전부 졌는데, **창을 하나가 아니라 여럿 주는 것**은 안 해봤습니다
(STEP 54 는 2단계만). 네모가 조금 어긋나도 이웃 창이 병변을 잡을 수 있고, 대신 창이 많아지면 헛알림도 늘 수 있습니다.

## 설계 (`tools/stage1_multiwindow.py`)

| 점수 | 창 |
|---|---|
| `user` (지금 배포, 비교 기준) | 사용자 중심 창 1 |
| `label` 상한 · `center` 하한선 | 라벨 중심 1 · 화면 중앙 1 |
| `user_g3s160` | 사용자 중심 3×3, 간격 160px(반 겹침) → **max** / mean / 상위 3 평균 |
| `user_g3s320` | 사용자 중심 3×3, 간격 320px(안 겹침, 960px 덮음) → 같음 |
| `grid5` ★ | 사진 전체 5×5, 간격 190px — **네모를 아예 안 씀** → 같음 |
| `label_g3s160` | 위치 민감도 계산용(라벨 중심 3×3) |

표본: fold 0 병변 2,500 + 정상 586, seed 31, STEP 50~54 와 **같은 난수 순서** → 같은 사진·같은 사용자 중심. 1단계 모델·문턱은 배포 그대로.

## 관문 — 돌리기 전에 못 박음

| | 값 |
|---|---|
| **주 관문** | 현 1단계(`user`)의 recall 에 맞춘 문턱에서 **헛알림 −5%p 이상** (STEP 52 와 같은 잣대) |
| 부관문 | AUROC ≥ `user` |
| 찍기만 | 위치 민감도 = 라벨 중심 − 사용자 중심 recall(raw 문턱): 창 하나 vs 3×3 · `grid5` 가 통과하면 "네모 없는 1단계" 후보 |

판정: 후보 / 구분 불가 / 기각. 통과해도 2단계 커버리지(3팔)와 holdout 을 거쳐야 배포. max 는 헛알림을 올리는 쪽으로 편향되므로
**max·mean·상위3 셋을 다 찍되 관문은 각각 따로** 봅니다(사후에 제일 좋은 걸 고르지 않도록 셋 다 적습니다).

- **주 관문 통과**: 사용자 중심 3×3(반 겹침) 평균·상위3 평균이 같은 recall 에서 헛알림 −5.5 / −6.0%p, AUROC +0.03 / +0.04. 셋 중 max 만 0.2%p 모자람 — 사전등록대로 셋을 다 적습니다.
- **위치 민감도가 거의 사라집니다**: 라벨 중심 − 사용자 중심 recall 차이(raw 문턱)가 창 하나 **+13.7%p → 3×3 max +1.5%p.** 즉 "네모를 어디 그리느냐에 따라 결과가 달라진다" 가 이 방식에선 거의 없어집니다.
- **네모는 여전히 필요합니다**: 사진 전체를 5×5 로 훑는 `grid5` 는 user 와 같음(기각). 창 간격을 320 으로 벌려도(안 겹침) 기각 — **사용자 중심 주변 ±160px 안**에서 촘촘히 보는 것이 값입니다.
- ⚠️ raw 문턱(0.1466)은 창 하나 기준이라 평균 점수엔 안 맞습니다(mean 에서 recall 89.6% / 헛알림 47.6%). 채택하려면 **문턱을 val 에서 다시** 뽑아야 합니다. 관문 값은 recall 을 맞춘 비교라 문턱과 무관합니다.
- 비용: 1단계 추론 9배 (effnetv2_s 320 창, CPU 서버에서 장당 수십 ms → 수백 ms). 2단계 3팔에 비하면 작습니다.
