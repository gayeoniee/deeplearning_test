# STEP 48 — 앱 입력 경로 프록시: photo+safe 후보 **제외** (2026-09-10)

STEP 46 이 `photometric` 복원을 확인했고, 그 위에 멘토 제안(병변 보존 random crop,
`safe`)을 얹은 **photo+safe 동결 후보**가 있었습니다. 개발 서버에 연결하기 전에
**앱 입력 형태를 거쳐도 깨지지 않는지**를 봤습니다.

> ⚠️ **실사용 성능 평가가 아닙니다 — 연결 검사입니다.** 판정 기준이 **비대칭**입니다:
> 좋게 나와도 *"실사용에서 더 정확"* 이라 말할 수 없고, **크게 나쁘거나 오류가 나면
> 배포 후보에서 제외**합니다. 이 페이지의 결론은 후자입니다.

**Mac MPS · 5,727장(VL01 reserved, 284개체) · 26.1분(듀티 50% 포함) · 열 경고 0건**

재현: `uv run --extra train python tools/eval_vl01_app_path.py --out data/work/vl01_app_path_eval/full`

## 왜 졌나 — 정상 피부를 알아보는 능력을 잃었습니다

### ① 문턱 탓이 아닙니다 (STEP 44 와 반대 모양)

```
AUROC   배포 0.8745  /  후보 0.7915   (−0.083 — 잡음 ±0.02 의 4배)
```

STEP 44 는 macro-F1 이 반토막인데 **AUROC 는 위**여서 *"문턱이 밀린 것"* 이었습니다.
이번엔 **AUROC 자체가 내려갔습니다.** 문턱을 공정하게 맞춰도 안 됩니다:

| 같은 recall 에서 오탐 | 배포 | 후보 | |
|---|---:|---:|---:|
| recall 0.95 | 1,256 | 1,887 | +631 |
| recall 0.97 | 1,468 | 2,085 | +617 |
| recall 0.98 | 1,655 | 2,297 | +642 |

어느 문턱이든 **정상 개 약 600마리를 더** 병원에 보냅니다.

### ② 피해가 정상 사진에 몰려 있습니다

| 이상 확률 중앙값 | 배포 | 후보 |
|---|---:|---:|
| 이상 사진 (2,759장) | 0.948 | 0.908 |
| **정상 사진 (2,968장)** | **0.157** | **0.683** |
| **둘 사이 간격** | **0.792** | **0.225** |

이상 사진 판단은 거의 그대로(−0.04)인데 **정상 사진이 0.157 → 0.683 으로 밀렸습니다.**
배포는 정상·이상을 0.79 벌려 놓는데 후보는 **0.23** — 거의 못 가릅니다.

| 겹침 | 장수 |
|---|---:|
| 둘 다 틀림 | 1,352 |
| 배포만 틀림 | 244 |
| **후보만 틀림** | **751 — 그중 정상(A7) 669장 (89%)** |
| 둘 다 맞음 | 3,380 |

후보만 틀린 정상 669장을 배포는 **중앙값 0.062** 로 봤고, 30% 는 0.05 미만 —
**배포가 확신 있게 정상이라고 한 사진들**입니다.

### ③ ⚠️ A6(결절·종괴)를 놓치기 시작합니다

## 판정

**후보를 배포 후보에서 제외합니다.** 배포 1단계(`effnetv2_s` + `f320` + `photometric`)를
유지합니다.

### 멘토 제안에 대해 — 정확히 말하면

*"판단할 수 없다"* 도 *"많이 흔들린다"* 도 **아닙니다.**

> **이 데이터·이 구현에서는 성능을 못 냅니다 — 두 번 재서 두 번 졌습니다.**
> STEP 45 (고정 ROI vs 보존 ROI, F1 −0.040 · AUROC −0.036) 와 이번(F1 −0.110 ·
> AUROC −0.083). 이번 후보는 `photometric` 까지 얹은 **가장 유리한 판**이었는데 더
> 크게 졌습니다.

실사용 사진에서 어떨지는 못 잽니다 — **그건 배포 모델도 마찬가지**라 후보에게만
불리한 조건이 아닙니다.

### 가설 — 증명이 아닙니다

`safe` crop 은 **병변을 보존**하는 크롭입니다. 이상 사진은 항상 병변이 창 안에
있게 잘리는데, **정상 사진은 보존할 병변이 없어서** 크롭 분포가 달라집니다. 모델이
*"이런 구도면 이상"* 을 배웠을 수 있습니다 — 피해가 정상 사진에 몰린 것과 맞습니다.
확인하려면 정상 사진의 크롭 방식을 고정한 대조 실험이 필요합니다. **지금 기간엔
안 합니다.** 아이디어가 틀렸다고까진 못 하고, **이 구현으로는 안 된다**까지입니다.

## ⚠️ 인용하면 안 되는 숫자

**배포 모델도 이 프록시에서 정상의 51%(1,522/2,968)를 병원에 보냅니다.** 이건
**고정 40% 네모 + JPEG 재압축이라는 일부러 가혹한 프록시** 탓이고, holdout
헛알림 18.7% 와 다른 숫자입니다. **두 모델의 차이**가 이 검사의 결론이지 배포
모델의 절대값이 아닙니다. 발표에서 51% 를 배포 성능처럼 말하면 틀립니다.

## 곁가지 — 실행에서 배운 것

- **시간 추정이 6배 빗나갔습니다.** 80분 예상이었는데 듀티 50% 를 걸고도 26분

  빗나가서, *"중지했다"* 고 답한 뒤에도 12분을 더 돌았습니다.
