# 08. 2단계 파이프라인 — 조용히 틀리는 여섯 가지

> 읽는 시점: STEP 4 시작 전, 그리고 성능 숫자를 보고할 때마다.

우리 모델은 한 덩어리가 아니라 **두 개를 이어붙인 것**입니다.

```
사진 ──▶ 1단계 ─── 이상확률 < 임계값 ──▶ "정상으로 보입니다"  (2단계는 안 돌아감)
                 └─ 임계값 이상 ───────▶ 2단계 ──▶ "A2 소견이 의심됩니다"
```

이어붙인 시스템에는 **한 덩어리 모델에는 없는 함정**이 있습니다.
전부 에러 없이 그럴듯한 숫자를 만들어내기 때문에 특히 위험합니다.

---

## 1. 단계별로 분할을 따로 하면 누수가 생깁니다

가장 치명적입니다. 그리고 가장 자연스럽게 저지릅니다.

```python
# ❌ 이렇게 하면 안 됩니다
s1 = make_binary_labels(df)
s1_tr, s1_va = train_test_split(s1)     # 여기서 한 번 나누고

s2 = df[df.label != "A7"]
s2_tr, s2_va = train_test_split(s2)     # 여기서 또 나눔
```

두 번 나누면 **1단계 검증에 쓴 강아지가 2단계 학습에 들어갑니다.**
그러면 파이프라인 전체를 평가할 때, 그 강아지는 2단계에게 이미 본 사진입니다.
점수가 부풀려지는데 어디서 부풀려졌는지 알 수도 없습니다.

```python
# ✅ 한 번만 나누고, 두 단계가 그 분할을 공유합니다
df = split.assign(df, cfg)              # fold / is_holdout / group 부여 (로컬에서 이미 끝남)
s1_all = stages.to_stage1(df)           # 같은 fold 컬럼을 물려받음
s2_all = stages.to_stage2(df)           # 같은 fold 컬럼을 물려받음
```

`stages.to_stage1/to_stage2` 는 라벨 컬럼만 바꾸고 `fold`/`is_holdout`/`group` 은
그대로 둡니다. 그래서 두 단계의 fold 0 은 **정확히 같은 개체 집합**입니다.

`tests/test_stages.py::test_stage_views_share_one_split` 이 이걸 감시합니다.

→ 자세한 내용: [`02_데이터_누수_가장_치명적인_함정.md`](02_데이터_누수_가장_치명적인_함정.md)

## 2. 크롭이 정답을 흘립니다 (지름길, shortcut)

이 데이터에서 실제로 확인해야 하는 함정입니다.

**A7(정상) 이미지에도 `labelingInfo` 박스가 있습니다.** 라벨러가 "촬영한 피부 부위"를
표시해 둔 것이고, 그 자체는 문제가 아닙니다. 문제는 그 박스로 ROI 크롭을 할 때입니다.

만약 정상 박스가 병변 박스보다 계통적으로 크다면:

```
정상 사진  → 넓은 박스 → 넓게 크롭 → 축소되어 저장  → 화면에 넓은 영역
병변 사진  → 좁은 박스 → 좁게 크롭 → 확대되어 저장  → 화면에 확대된 피부
```

이러면 모델은 피부를 볼 필요가 없습니다. **확대 배율만 세면 됩니다.**
그리고 이 지름길은 검증 점수를 **높게** 만듭니다 — 검증셋도 같은 방식으로
크롭됐으니까요. 실제 보호자 사진에는 박스가 없으니 배포하면 무너집니다.

같은 종류의 지름길이 하나 더 있습니다: **사진 화질**.
정상 사진과 병변 사진의 촬영 조건(조명, 초점)이 계통적으로 다르면
모델이 "선명하면 병변" 같은 규칙을 배울 수 있습니다.

### VL01 실측 — 둘 다 걸렸습니다

```
(a) 정상 0.71%  vs  병변 1.25%          → 0.57배   🚨 정상이 더 확대됨
(b) A1 0.47%    ~   A6 3.08%            → 6.5배    🚨 병변끼리도 다름
    초점: 정상 39  vs  병변 271          → 7배      🚨
```

**`[1]`과 `[3]`은 같은 원인입니다.** 박스가 작으면 → 같은 224px 로 맞추느라 더 확대되고
→ 확대하면 흐려집니다. 정상이 가장 작고(0.71%) 가장 흐립니다(39).
별개의 두 문제가 아니라 하나이고, 배율을 고치면 화질 격차도 함께 완화됩니다.

`(b)` 가 특히 나쁩니다. A6(결절·종괴)는 **종양 감별이 필요한** 클래스인데
박스가 6.5배 크므로 "크면 A6" 라는 규칙이 성립할 수 있습니다.

### 확인 방법

```python
report = crop.audit(d, cfg=CFG(img_size=224))    # 배율·화질·좌표 5가지 판정
floor  = crop.shortcut_baseline(d)               # ★ 실제 피해량
```

`shortcut_baseline()` 이 결정적입니다. **픽셀을 한 장도 안 보고** 박스 크기·종횡비·
크롭 창 크기만으로 분류기를 학습시켜 봅니다. 거기서 나온 점수가 CNN 이 넘어야 하는
**하한선**이고, 같은 `fold` 를 쓰므로 CNN 점수와 직접 비교됩니다.

```
CNN macro-F1 0.45  vs  하한선 0.40   →  피부에서 얻은 건 0.05 뿐   🚨
CNN macro-F1 0.45  vs  하한선 0.18   →  대부분 피부에서 얻음       ✅
```

"배율 차이가 있다" 와 "그래서 얼마나 손해인가" 는 다른 질문입니다.
경고만 보고 대응하면 필요 없는 재작업을 하게 되니, 하한선을 먼저 재세요.

### 대응

**1단계 — `full` 크롭.** 박스를 쓰지 않고 중앙 정사각으로 자르므로 배율 정보가
사라집니다. 노트북 03 이 감사 결과를 보고 자동으로 정합니다:

```python
SCALE_GAP = report.get("area_ratio_normal_over_lesion", 1.0)
STAGE1_CROP = "full" if (SCALE_GAP > 1.5 or SCALE_GAP < 0.67) else BEST_CROP
```

**2단계 — 고정 픽셀 크롭.** `full` 은 병변이 너무 작아져 쓸 수 없습니다
(0.5~3% 면적). 대신 병변 중심에서 **항상 같은 픽셀 수**를 잘라냅니다:

```
margin 1.5   병변 40px  → 창 60px  → 224px 로 확대 (3.7배)   배율이 다름 ❌
             병변 260px → 창 390px → 224px 로 축소 (0.6배)

f320         병변 40px  → 창 320px → 224px (0.7배)           배율이 같음 ✅
             병변 260px → 창 320px → 224px (0.7배)
```

피부 1mm 가 항상 같은 픽셀 수라 배율로 맞히는 경로가 막힙니다.
대신 **큰 병변은 창을 넘어 잘립니다** — 그게 대가입니다. A6(결절·종괴)처럼 큰 병변은
전체 형태를 못 볼 수 있으니, `f320` 과 `m1.5` 를 비교해서 정하세요.

만드는 방법 (로컬, 원본이 있어야 합니다):

```cmd
py prepare_local.py --chunk VL01 --margins -320   # 음수 = 고정 픽셀 창
py prepare_local.py --finalize
py prepare_local.py --package
```

기존 크롭은 그대로 두고 `f320` 태그만 추가되므로 크롭 비교에 자동 포함됩니다.

> ⚠️ **점수가 떨어집니다.** 그게 정직한 숫자입니다.
> 지름길이 막힌 상태의 낮은 점수가, 지름길이 열린 상태의 높은 점수보다 실제에 가깝습니다.

> 💡 `crop._window()` 가 창을 정하는 **단 하나의** 함수입니다. 크롭을 만들 때
> (`_crop_one`)와 나중에 좌표를 복원할 때(`crop_window`, Grad-CAM 게이트용) 모두
> 이걸 씁니다. 두 곳에 같은 로직을 두면 갈라지고, 갈라지면 게이트가 거짓말합니다.
> `tests/test_crop_geometry.py::test_window_is_single_source_of_truth` 가 감시합니다.

### 두 단계가 다른 크롭을 쓸 때 반드시 할 일

각 모델에는 **그 모델이 학습한 크롭**을 먹여야 합니다. 파이프라인 평가에서
같은 `DataFrame` 을 두 모델에 그냥 넣으면 한쪽이 처음 보는 크롭을 받습니다:

```python
va_s2 = crop.switch_tag(va_all, BEST_CROP, verbose=False)   # 2단계용으로 경로만 교체
dl1, ds1 = data.eval_loader(va_all, cfg1, model=m1, classes=CLASSES_STAGE1)
dl2, ds2 = data.eval_loader(va_s2,  cfg2, model=m2, classes=CLASSES)
assert len(ds1.df) == len(ds2.df)
assert (ds1.df["image_name"].to_numpy() == ds2.df["image_name"].to_numpy()).all()
```

`switch_tag()` 는 `image_path` 해시로 경로를 다시 계산하므로 행 순서가 보존됩니다.
그래도 `assert` 두 줄은 넣으세요 — 어긋나면 에러 없이 틀린 점수가 나옵니다.

## 3. 각 단계의 점수를 곱하면 낙관적으로 나옵니다

흔한 보고 방식:

> "1단계 recall 0.95, 2단계 macro-F1 0.75 → 대략 0.71 정도 되겠네요"

이 곱셈은 **두 단계의 오류가 서로 독립이라고 가정**합니다. 실제로는 그렇지 않습니다.
1단계가 놓치기 쉬운 사진(병변이 작고 흐릿한 사진)은
2단계도 틀리기 쉬운 사진입니다. 오류가 **같은 사진에 몰립니다.**

그래서 이 리포에는 두 함수가 있습니다:

| 함수 | 방식 | 언제 |
|---|---|---|
| `stages.report_pipeline()` | 곱셈 추정치 | 학습 중 감 잡기 |
| **`stages.pipeline_report()`** | 같은 집합에 이어붙여 실측 | **보고할 때** |

`pipeline_report()` 는 정상 사진까지 포함한 하나의 집합에 두 모델을 돌려
최종 7종(A1~A6 + A7) 혼동행렬을 만듭니다. 이게 사용자가 겪는 성능입니다.

## 4. 2단계 평가용 데이터에 정상 사진을 빼먹습니다

2단계는 병변 6종만으로 **학습**합니다. 맞습니다.
그런데 **평가**할 때 병변만 넣으면 실제 상황과 다릅니다.

실제 서비스에서는 정상 사진도 1단계를 통과하면(= 오탐) 2단계로 넘어옵니다.
그때 2단계는 A1~A6 중 하나를 반드시 고릅니다 — 정상이라고 말할 선택지가 없으니까요.
그 사진이 어떤 라벨을 받는지가 오탐의 실제 내용입니다.

```python
# ✅ 평가는 정상 포함 전체 집합에, 두 모델 모두
va_all = split.get_fold(s1_all, 0)[1]                  # 정상 + 병변
dl1, ds1 = data.eval_loader(va_all, cfg1, model=m1, classes=CLASSES_STAGE1)
dl2, ds2 = data.eval_loader(va_all, cfg2, model=m2, classes=CLASSES)
assert (ds1.df["image_name"].to_numpy() == ds2.df["image_name"].to_numpy()).all()
```

`data.eval_loader()` 는 `shuffle=False` 로 **행 순서를 보존**합니다.
순서가 어긋나면 1단계의 3번째 사진 점수가 2단계의 3번째 사진 예측과 짝지어져
**에러 없이 완전히 틀린 숫자**가 나옵니다. 그래서 위 `assert` 를 반드시 넣으세요.

## 5. 임계값을 holdout 에서 고릅니다

임계값도 **학습해야 하는 파라미터**입니다. 모델 가중치와 다를 게 없습니다.

- 검증셋에서 "recall 0.95 를 만족하는 가장 큰 임계값" 을 고릅니다
- holdout 에서는 그 값을 **적용해서 확인만** 합니다

holdout 에서 recall 이 0.93 으로 나왔다고 임계값을 낮추면,
그 순간 holdout 은 더 이상 미지의 데이터가 아닙니다.
그때 할 일은 임계값 수정이 아니라 **정직한 보고**입니다:

> "검증셋 기준으로 정한 임계값 0.31 을 적용했을 때 holdout 스크리닝 recall 은 0.93 이었습니다."

노트북 05 는 참고용으로 "holdout 기준 최적값" 도 출력하지만,
**그 값을 채택하지 말라고 명시**해 둡니다. 두 값의 차이는 검증셋 크기나
분포 차이를 보여주는 진단 정보입니다.

## 6. 임계값 하나가 시스템의 성격을 결정합니다

임계값을 낮추면:

| | 놓친 병변 | 헛알림 |
|---|---|---|
| 임계값 ↓ | **줄어듦** ✅ | 늘어남 ❌ |
| 임계값 ↑ | 늘어남 ❌ | 줄어듦 ✅ |

이 프로젝트의 목적("의심된다까지 알려주기")에서는 **놓치지 않는 쪽**이 맞습니다.
병원에 헛걸음하는 비용과 병을 놓치는 비용이 전혀 다르니까요.

다만 무한정 낮추면 안 됩니다. 헛알림이 너무 많으면
보호자가 알림을 **아예 무시**하게 됩니다. 그러면 놓친 병변이 0이어도 소용없습니다.
경보 피로(alarm fatigue)는 의료 시스템에서 잘 알려진 실패 양식입니다.

실무 기준:

- 스크리닝 recall ≥ 0.95 를 만족하는 **가장 큰** 임계값을 고릅니다
  (= 그 조건에서 헛알림이 최소인 지점)
- 헛알림 비율이 50% 를 넘으면 임계값을 다시 보거나 1단계 모델을 개선합니다
- 노트북 03 의 임계값 표를 보고 직접 눈으로 교환관계를 확인하세요

## 보고할 때 쓸 숫자

파이프라인 성능을 한 줄로 말해야 한다면 **이 두 개**입니다:

```
스크리닝 recall  0.95   ← 병변이 있는 강아지 중 병원 안내를 받은 비율
헛알림 비율      0.38   ← 정상인데 병원 안내를 받은 비율
```

여기에 종류 정확도를 덧붙입니다:

```
병변 종류 정확도  0.71   ← 병원 안내를 받은 병변 중 형태까지 맞힌 비율
```

**"macro-F1 0.78" 만 말하는 건 이 프로젝트에서 불충분합니다.**
그 숫자는 2단계만의 성적이거나, 정상 사진을 뺀 성적이기 쉽습니다.

## 체크리스트

- [ ] 분할은 한 번만 했고 두 단계가 공유한다 (`split.verify()` 를 두 뷰 모두에)
- [ ] `crop.audit()` 을 돌려 배율·화질 지름길이 없는지 확인했다
- [ ] `crop.shortcut_baseline()` 하한선을 재고, CNN 이 그걸 유의미하게 넘는지 확인했다
- [ ] 두 단계가 다른 크롭을 쓴다면 각 모델에 맞는 크롭을 먹였다 (행 정렬 assert)
- [ ] 파이프라인 평가는 정상 포함 전체 집합에서 했다
- [ ] 두 로더의 행 순서 일치를 `assert` 로 확인했다
- [ ] 임계값은 검증셋에서 정했고 holdout 은 확인만 했다
- [ ] 보고 숫자는 `pipeline_report()` 결과다 (곱셈 추정치가 아니다)
- [ ] 헛알림 비율도 함께 보고했다
