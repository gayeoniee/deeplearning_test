## `.fit()` 안에는 뭐가 있나

sklearn 에서는 `model.fit(X, y)` 한 줄이었죠. PyTorch 는 그 안을 직접 씁니다.
겁먹을 필요 없습니다. **핵심은 4줄**입니다:

```python
for x, y in dataloader:
    pred = model(x)              # 1. 순전파 — 예측
    loss = criterion(pred, y)    # 2. 얼마나 틀렸나
    loss.backward()              # 3. 역전파 — 각 가중치의 책임 계산
    optimizer.step()             # 4. 그 반대 방향으로 조금 이동
    optimizer.zero_grad()        #    기울기 초기화
```

나머지 코드는 전부 **"이걸 빠르고 안정적으로 하는 장치"** 입니다.

---

## 1. 순전파와 역전파

**순전파**: 입력 → 층들 통과 → 출력. 그냥 계산입니다.

**역전파**: "최종 오차에 각 가중치가 얼마나 기여했나"를 **뒤에서부터** 계산.
고등학교 미적분의 **연쇄법칙(chain rule)** 그 자체입니다.

```
loss ← 출력층 ← 은닉층3 ← 은닉층2 ← 은닉층1
 └──────── 기울기가 뒤로 흐름 ────────┘
```

PyTorch 가 `loss.backward()` 한 줄로 자동으로 해줍니다 (autograd).
직접 미분할 일은 없습니다.

> ⚠️ `optimizer.zero_grad()` 를 빠뜨리면 기울기가 **누적**됩니다.
> 이전 배치의 기울기가 남아 학습이 이상해집니다. 가장 흔한 초보 실수입니다.

---

## 2. 옵티마이저 — AdamW 를 쓰세요

`optimizer.step()` 이 "어떻게 이동할지"를 정합니다.

| | SGD | Adam | **AdamW** |
|---|---|---|---|
| 방식 | 기울기 방향으로 일정하게 | 파라미터마다 보폭 자동 조절 | Adam + weight decay 분리 |
| 튜닝 | 어려움 | 쉬움 | 쉬움 |
| 현재 표준 | 일부 CNN | | **✅ 대부분** |

```python
optimizer = torch.optim.AdamW(param_groups(model, cfg))
```

**AdamW 의 'W'**: Adam 은 weight decay 를 기울기에 섞어 넣어서
적응적 보폭과 충돌했습니다. AdamW 는 이걸 분리했고, 그게 더 잘 됩니다.
2026년 기준 트랜스포머·현대 CNN 파인튜닝의 사실상 표준입니다.

### 학습률 (lr) — 가장 중요한 하이퍼파라미터

```python
cfg = CFG(lr=3e-4)
```

| 증상 | 원인 | 대응 |
|---|---|---|
| loss 가 NaN / 폭발 | lr 너무 큼 | 10배 낮추기 |
| loss 가 출렁이며 안 내려감 | lr 큼 | 3배 낮추기 |
| loss 가 너무 천천히 내려감 | lr 작음 | 3배 올리기 |
| 처음엔 좋다가 정체 | 스케줄러 필요 | cosine 사용 (기본 적용됨) |

파인튜닝 기본값: **헤드 1e-4 ~ 5e-4, 백본은 그 1/10.**

## 3. 스케줄러 — lr 을 시간에 따라 바꾸기

고정 lr 은 좋지 않습니다. 초반엔 크게 움직이고 후반엔 미세조정해야 하니까요.

우리가 쓰는 건 **cosine annealing + warmup**:

```
lr
 │      ╱‾‾‾╲___
 │     ╱        ‾‾‾╲___
 │    ╱                ‾‾‾╲__
 │   ╱                        ‾‾╲_
 └──┴──────────────────────────────→ step
   warmup        cosine 감쇠
```

```python
scheduler = cosine_with_warmup(optimizer,
                               warmup_steps=cfg.warmup_epochs * steps_per_epoch,
                               total_steps=cfg.epochs * steps_per_epoch)
```

- **warmup** (앞 2에폭): 0 → 목표 lr. 랜덤 헤드의 큰 기울기가 백본을 망가뜨리는 걸 방지
- **cosine 감쇠**: 부드럽게 감소. 계단식(StepLR)보다 대체로 성능이 좋습니다

> ⚠️ `scheduler.step()` 은 **에폭이 아니라 스텝마다** 부릅니다 (우리 구현이 그렇습니다).
> 옛날 코드는 에폭마다 부르는 경우가 많아 헷갈릴 수 있습니다.

---

## 4. AMP — 공짜로 2배 빨라지기

**혼합 정밀도(Automatic Mixed Precision)**: 계산을 float32 대신
float16/bfloat16 으로 합니다.

```python
cfg = CFG(amp=True)   # 기본값
```

- ✅ 속도 1.5~3배
- ✅ 메모리 절반 → 배치를 2배로 키울 수 있음
- ✅ 정확도 손실 거의 없음

**fp16 vs bf16:**

| | fp16 | bf16 |
|---|---|---|
| 표현 범위 | 좁음 → **언더플로 위험** | 넓음 (fp32 와 동일) |
| GradScaler | **필요** | 불필요 |
| 지원 | 모든 최신 GPU | Ampere 이상 (A100, L4, RTX30xx+) |

T4 는 bf16 미지원이라 fp16 + GradScaler 를 씁니다.
GradScaler 는 loss 를 크게 곱했다가 되돌려서 작은 기울기가 0으로 사라지는 걸 막습니다.

우리 코드가 자동 판별합니다:
```python
amp_dtype = torch.bfloat16 if env.device_info().bf16 else torch.float16
use_scaler = cfg.amp and device == "cuda" and not env.device_info().bf16
```

---

## 5. 기울기 누적 — VRAM 없이 배치 키우기

배치 64로 돌리고 싶은데 VRAM 이 16으로 꽉 찬다면:

```python
cfg = CFG(batch_size=16, grad_accum=4)   # 실효 배치 64
```

4번 순전파/역전파를 하고 기울기를 쌓아뒀다가 **한 번만** 업데이트합니다.

```python
loss = loss / cfg.grad_accum      # 평균이 되도록 나눔
loss.backward()                    # 기울기 누적

if (step + 1) % cfg.grad_accum == 0:
    optimizer.step()               # 4번에 한 번만
    optimizer.zero_grad()
```

> 💡 완전히 같지는 않습니다. BatchNorm 통계는 여전히 16개 기준입니다.
> 그래도 큰 모델을 작은 GPU 에서 돌리는 표준 방법입니다.

---

## 6. 기울기 클리핑 — 폭주 방지

```python
torch.nn.utils.clip_grad_norm_(model.parameters(), cfg.clip_grad_norm)
```

기울기 전체의 크기가 임계값(1.0)을 넘으면 비율대로 줄입니다.
가끔 나오는 이상한 배치 하나가 가중치를 날려버리는 걸 막습니다. 보험입니다.

---

## 7. EMA — 공짜 성능 향상

**지수이동평균**: 학습 중 가중치의 이동평균을 따로 유지합니다.

```python
cfg = CFG(ema_decay=0.999)
```

```python
ema_weight = 0.999 * ema_weight + 0.001 * current_weight
```

**왜 좋은가**: 학습 후반에 가중치는 최적점 주변을 진동합니다.
그 궤적의 **평균**이 어느 한 순간의 가중치보다 대체로 낫습니다.

보통 macro-F1 **+0.3~1%p** 정도 공짜로 얻습니다. 안 쓸 이유가 없습니다.
우리 `train.fit()` 은 검증도 EMA 가중치로 하고, 체크포인트에 둘 다 저장합니다.

---

## 8. 조기 종료 — 무엇을 기준으로?

```python
cfg = CFG(monitor="macro_f1", early_stop_patience=5)
```

> ⚠️ **accuracy 를 기준으로 삼지 마세요.**
> 불균형 데이터에서는 "다수 클래스만 맞히는 모델"이 높은 accuracy 를 받습니다.
> A5(미란·궤양)를 전부 놓쳐도 accuracy 는 좋을 수 있습니다.

`macro_f1` 은 모든 클래스를 동등하게 취급하므로 희소 클래스를 버리면 떨어집니다.
우리 목적(놓치지 않기)에 맞는 기준입니다.

`patience=5` = 5에폭 동안 개선이 없으면 중단. 시간 낭비를 막습니다.

## 전체 그림

```python
for epoch in range(cfg.epochs):
    # ── 학습 ──
    model.train()                          # BN/Dropout 학습 모드
    for step, (x, y) in enumerate(dl_train):
        with autocast(dtype=amp_dtype):    # AMP
            loss = criterion(model(x), y) / cfg.grad_accum
        scaler.scale(loss).backward()      # 역전파

        if (step+1) % cfg.grad_accum == 0:
            scaler.unscale_(optimizer)
            clip_grad_norm_(...)           # 폭주 방지
            scaler.step(optimizer)         # 가중치 갱신
            scaler.update()
            optimizer.zero_grad()
            scheduler.step()               # lr 조정
            ema.update(model)              # EMA 갱신

    # ── 검증 ──
    model.eval()                           # BN/Dropout 추론 모드
    with torch.no_grad():                  # 기울기 계산 끄기 (메모리 절약)
        ...
    if score > best: save_checkpoint()
    elif no_improve >= patience: break
```

`src/train.py` 의 `fit()` 이 정확히 이 구조입니다.

| 패턴 | 진단 | 처방 |
|---|---|---|
| train↓ val↓ 계속 | 정상, 여유 있음 | epochs 늘리기 |

| train 만 0에 붙음 | 심한 과적합 | 데이터 늘리기, 모델 줄이기 |

## 흔한 오해 3가지

**❌ "epoch 을 많이 돌릴수록 좋다"**
과적합 지점을 지나면 오히려 나빠집니다. 조기 종료가 있는 이유입니다.

**❌ "loss 가 낮으면 좋은 모델"**
loss 와 macro-F1 이 항상 같이 가지 않습니다. 특히 class weight 를 쓰면요.
**우리가 실제로 원하는 지표**로 판단하세요.

**❌ "model.eval() 은 안 불러도 된다"**
반드시 불러야 합니다. BatchNorm 과 Dropout 의 동작이 달라집니다.
안 부르면 추론 결과가 배치 구성에 따라 바뀝니다.
