# 02. 이미지는 어떻게 숫자가 되나

> **읽는 시점**: STEP 3(전처리) 전

---

## 이미지 = 숫자 3차원 배열

강아지 피부 사진 한 장은 컴퓨터에게 이렇게 생겼습니다:

```
높이 480 × 너비 640 × 채널 3 (RGB)
= 921,600 개의 숫자
```

각 숫자는 0~255. 예를 들어 왼쪽 위 첫 픽셀이 `(210, 180, 170)` 이면
빨강 210, 초록 180, 파랑 170 → 연한 살구색입니다.

```python
from PIL import Image
import numpy as np

img = Image.open("dog.jpg").convert("RGB")
arr = np.array(img)
print(arr.shape)     # (480, 640, 3)
print(arr[0, 0])     # [210 180 170]
print(arr.dtype)     # uint8  (0~255 정수)
```

> 💡 표 데이터가 `(행, 열)` 2차원이었다면 이미지는 `(높이, 너비, 채널)` 3차원,
> 배치까지 합치면 `(배치, 채널, 높이, 너비)` 4차원입니다.

---

## PyTorch 의 채널 순서 (헷갈리는 지점 1위)

```
PIL / OpenCV / matplotlib :  (H, W, C)   ← 높이, 너비, 채널
PyTorch                   :  (C, H, W)   ← 채널이 앞!
```

PyTorch 가 `(C, H, W)` 를 쓰는 이유는 합성곱 연산에서 메모리 접근이 효율적이기 때문입니다.

**증상**: 이미지를 띄웠는데 이상한 색 줄무늬가 보이면 순서가 꼬인 겁니다.

```python
# 텐서를 matplotlib 으로 보려면 되돌려야 함
plt.imshow(tensor.permute(1, 2, 0))    # (C,H,W) → (H,W,C)
```

노트북 03의 "증강 후 이미지 보기" 셀에 이 변환이 들어 있습니다.

## 전처리 3단계

### 1) 리사이즈 — 크기를 통일

신경망은 **고정 크기 입력**을 받습니다. 우리 데이터는 사진마다 해상도가 다르니
전부 같은 크기로 맞춰야 합니다.

```python
T.Resize(256)          # 짧은 변을 256으로 (종횡비 유지)
T.CenterCrop(224)      # 가운데 224×224 잘라내기
```

**왜 Resize 후 Crop 인가?** 그냥 `Resize((224,224))` 하면 종횡비가 찌그러집니다.
640×480 을 224×224 로 억지로 밀면 가로가 압축돼서 **둥근 구진이 타원**이 됩니다.
병변의 모양이 라벨의 단서인데 그걸 왜곡하면 안 되죠.

> 이 프로젝트의 `crop.py` 가 애초에 **정사각형으로** 크롭해서 저장하는 이유입니다.

### 2) ToTensor — 0~255 정수를 0~1 실수로

```python
T.ToTensor()
# uint8 (0~255), (H,W,C)  →  float32 (0.0~1.0), (C,H,W)
```

두 가지를 한꺼번에 합니다: 스케일 변환 + 축 순서 변경.

**왜 0~1로?** 신경망은 입력 값이 크면 학습이 불안정합니다.
255 같은 값이 층을 거치며 곱해지면 금방 폭발합니다.

### 3) Normalize — 평균 0, 표준편차 1 근처로

```python
T.Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])
# 계산: (x - mean) / std
```

이 숫자들은 **ImageNet 1400만 장의 채널별 평균·표준편차**입니다.
사전학습 모델이 이 통계로 학습됐으니 우리도 같게 맞춰야 합니다.

> ⚠️ **모델마다 다릅니다.** SigLIP/CLIP 계열은 `mean=[0.5,0.5,0.5]` 를 씁니다.
> 안 맞추면 사전학습의 이점을 상당 부분 날립니다.
>
> 그래서 `src/data.py` 의 `transforms_for_model()` 이
> `model.pretrained_cfg` 에서 자동으로 읽어옵니다:
> ```python
> mean = tuple(cfgd.get("mean", IMAGENET_MEAN))
> std  = tuple(cfgd.get("std",  IMAGENET_STD))
> ```

## 전체 흐름 정리

```
dog.jpg (640×480 JPEG, 120KB)
   │
   ├─ Image.open().convert("RGB")     → PIL (H=480, W=640, C=3), 0~255
   ├─ Resize(256) + CenterCrop(224)   → PIL (224, 224, 3)
   ├─ ToTensor()                      → Tensor (3, 224, 224), 0.0~1.0
   └─ Normalize(mean, std)            → Tensor (3, 224, 224), 약 -2.1~2.6
                                            │
   DataLoader 가 배치로 묶음  ──────────────┘
                                            ↓
                                    Tensor (32, 3, 224, 224)
                                            ↓
                                        모델 입력
```

---

## 우리 프로젝트에 특히 중요한 것: ROI 크롭

사전 조사에서 나온 사실:

> **병변이 이미지의 5% 미만인 경우가 93%**

224×224 로 리사이즈하면 병변이 차지하는 픽셀은:

```
전체 224×224 = 50,176 픽셀
병변 5%      =  2,509 픽셀  (약 50×50)
병변 1%      =    502 픽셀  (약 22×22)
```

**22×22 픽셀로 구진과 농포를 구분하라고요?** 사람도 못 합니다.

그래서 `crop.py` 가 병변 박스 주변만 잘라냅니다:

```
원본 640×480 에서 병변 100×100  →  리사이즈하면 병변이 35×35
크롭 150×150 (박스 1.5배)      →  리사이즈하면 병변이 149×149  ✅
```

같은 224×224 입력인데 **병변이 차지하는 정보량이 18배** 늘어납니다.

```python
crop.run(df, cfg, margin=1.5)
```

margin 을 얼마로 할지는 트레이드오프입니다:
- 작으면 (1.0): 병변만 크게 보이지만 **주변 정상 피부와 비교**할 맥락이 없음
- 크면 (3.0): 맥락은 있지만 병변이 다시 작아짐

→ 노트북 03에서 1.5 / 2.5 / full 세 가지를 **실험으로** 비교합니다.

## 해상도를 얼마로 할까

```python
cfg = CFG(img_size=224)   # 또는 288, 384...
```

| 해상도 | 메모리 | 속도 | 세밀함 |
|---|---|---|---|
| 224 | 1× | 1× | 기본 |
| 288 | 1.65× | 0.6× | 비듬·각질 질감이 살아남 |
| 384 | 2.9× | 0.34× | 더 세밀, T4 에서 버거움 |

**메모리와 시간은 해상도의 제곱에 비례합니다.**

피부 질감(A2 비듬·각질)은 고해상도가 유리하고,
큰 병변 형태(A6 결절)는 224로도 충분합니다.
우리 기본값은 절충인 288입니다.

## 흔한 실수 3가지

**❌ 검증에도 랜덤 증강 적용**
```python
# 검증 transform 에 RandomResizedCrop 이 들어가면
# 돌릴 때마다 점수가 달라집니다
```
`build_transforms(cfg, train=False)` 는 항상 결정론적입니다 (Resize + CenterCrop).

**❌ Normalize 를 빼먹거나 두 번 적용**
빼먹으면 성능이 확 떨어지고, 두 번 하면 값이 이상해집니다.
`transforms_for_model()` 하나만 쓰면 실수할 일이 없습니다.

**❌ 학습과 추론의 전처리가 다름**
가장 찾기 어려운 버그입니다. 학습은 288px, 추론은 224px 이면
모델은 잘 학습됐는데 실서비스에서만 성능이 나쁩니다.
`infer.Engine` 이 체크포인트에 저장된 `cfg` 를 그대로 쓰는 이유입니다.
