# 앱 연동 — 스크리닝 API

안드로이드 앱(**DAENGS_APP**)이 붙을 자리입니다.
아직 합치지 않았고, 합칠 때 알아야 할 것을 여기 모았습니다.

```
사진 → [서빙 크롭] → 1단계(정상/이상) ─ 낮으면 → "정상으로 보입니다"
                                       └ 높으면 → 2단계(6종 분포) → 진료 권함
```

| 파일 | 역할 |
|---|---|
| [`src/agent.py`](../src/agent.py) | 파이프라인 + **응답 계약** (HTTP 모름) |
| [`src/message.py`](../src/message.py) | 문구 생성. torch 안 씁니다 |
| [`serve.py`](../serve.py) | FastAPI 서버 + 데모 화면 |
| [`demo/index.html`](../demo/index.html) | 데모 UI — **DAENGS 챗봇 화면** 재현 |

### ★ "1등 병변" 필드가 없습니다 — 실수가 아닙니다

holdout 에서 그 이름이 **56.6% 틀렸습니다.** 필드로 주면 앱은 그걸 화면 제일 크게
띄웁니다. 그래서 계약에서 아예 뺐고, `tests/test_agent.py` 가 `top1` `predicted`
`diagnosis` 같은 키가 생기는지 감시합니다.

**앱 쪽 화면 규칙 — ★ 2026-09-08 개정** (`docs/cautions/03` §7-B):

카드는 **위에서 아래로** 이렇게 그립니다:

```
1. alert   가 null 이 아니면  →  맨 위 경고 상자 (text + action + caveat)
2. headline + stage1.abnormal_percent 게이지
3. group   이 null 이 아니면  →  한 줄 (group.text 를 **그대로**)
4. "어떤 병변인지까지는 이 사진만으로 판단할 수 없어요"   ← 항상, 숫자보다 위
5. groups  네 줄 막대 (같은 무게로)
6. action
7. disclaimer
```

1. **`groups` 네 개를 같은 무게로** 그립니다. 1등을 크게/굵게 쓰지 않습니다
2. **`distribution`(6종)은 안 그립니다.** 계약에는 있지만 보호자 화면엔 안 띄웁니다
3. `body`/"판단할 수 없어요" 를 **숫자보다 위에** 놓습니다
4. `disclaimer` 는 접거나 회색으로 숨기지 않습니다
5. **긴급도 문구를 앱이 자체적으로 붙이지 않습니다** — 이름을 단정하는 셈이고,
   묶음의 긴급도는 높은 쪽으로 잡혀 **말한 것의 절반이 부풀려집니다**(과잉 52.4%)
6. ★ **면책은 두 번까지.** 서버가 이미 4·7 두 번 합니다. 앱이 더 붙이지 마세요 —
   다섯 번 하던 걸 줄인 것입니다
7. ★ `group` / `alert` 가 `null` 이면 **그 줄을 통째로 안 그립니다.**
   확신이 낮을 때(약 3분의 1) `group` 이 null 이 되고 막대만 남습니다 —
   그게 *"확신 없으면 말하지 않는다"* 의 구현입니다

`verdict` 별로 `stage2.shown` 이 false 면 분포 영역을 통째로 그리지 않으면 됩니다.

## ⚠️ 아직 안 된 것 — 합치기 전에 읽어주세요

### 1. 가이드 프레임이 곧 bbox 입니다 — 크롭 어긋남은 대부분 풀렸습니다

> ## ⚠️⚠️ 2026-09-08 — **이 절의 낙관은 실측으로 뒤집혔습니다**
>
> 아래 *"0px 차이"* 는 **네모가 정확할 때**의 이야기입니다. 실제로 사람이
> 그리는 네모를 재보니 (STEP 36~39, `tools/box_error.py`):
>
> | 실측 | |
> |---|---|
> | 사람이 그린 네모 크기 | **병변 크기와 무관** (상관 **−0.05**) — 정답의 **2.80배** |
> | 그 네모가 화면에서 | **47.2 ~ 70.6%** |
> | `m2.5` 창 포화점 | **47%** (1080px 기준) → **40장 전부(100%) 포화** |
>
> ★ **즉 2단계는 사실상 사진 전체를 봅니다.** 크롭이 걸리지 않습니다.
>
> **실측 결과** (VL01, n=3,064): 계열 4군 커버리지가
> **라벨 네모 50.3% → 사용자 네모 22.4% (상대 −55.5%)**.
>
> ⚠️ **아래 밴드(`ALLOW 0.28~0.68`)는 포화점 0.47 을 한참 넘게 허용합니다** —
> **밴드를 통과해도 창이 포화됩니다.** 밴드는 `네모 ÷ 화면` 을 보는데 모델이
> 필요한 건 `네모 ÷ 병변` 이고, **앱은 병변을 못 보니 그걸 잴 수 없습니다.**
>
> 고치려던 일곱 갈래(크기 안내 · 기본값 조정 · 탭 · 모델 제안 · 잡음 증강 ·
> `f320` 전환 ×2)를 **전부 재고 전부 닫았습니다.** 지금 배포 구성이 사용자
> 네모에서 제일 낫습니다 — 자세한 것은
> [`STEP36~39 요약`](results/STEP36_39_요약_네모_이야기.md).

학습은 라벨 bbox 로 잘랐고 **보호자 사진에는 bbox 가 없다**는 게 원래 문제였습니다.
해법은 앱이 이미 띄워야 하는 것이었습니다 — **촬영 가이드 프레임을 bbox 로 받습니다.**

```
POST /v1/screen
  photo : 사진
  box   : "[0.28, 0.28, 0.44, 0.44]"   ← 정규화 [x, y, w, h] (0~1)
```

서버는 이걸 받아 **학습이 쓰는 바로 그 함수**(`crop.crop_window()`)를 부릅니다.
재구현하지 않습니다 — 두 곳에 같은 로직을 두면 갈라지고, 갈라지면 아무도 모릅니다.

**실측 (`tests/test_agent.py` [4]):** 1920×1080 원본의 bbox 로 만든 학습 크롭과,
같은 구도를 4032×2268 로 찍고 그 네모를 넘겼을 때의 서빙 크롭이 **0px 차이**로
같은 창이었습니다.

| | 학습 창 | 서빙 창 | 차이 |
|---|---|---|---|
| 1단계 `f320` | `(800, 380, 1120, 700)` | `(800, 380, 1120, 700)` | **0px** |
| 2단계 `m2.5` | `(785, 365, 1135, 715)` | `(785, 365, 1135, 715)` | **0px** |

해상도가 달라도 되는 이유: 넘어온 사진의 **짧은 변을 1080 으로 먼저 맞춥니다**
(`to_train_space`). 원본이 전부 1920×1080 이었으므로, 그 뒤로는 f320 의 320 이
학습 때와 같은 화각을 뜻합니다.

#### ⚠️ 그래도 두 단계의 사정이 다릅니다

| | bbox 를 어떻게 쓰나 | 네모가 부정확하면 |
|---|---|---|
| **1단계 `f320`** | **중심만.** 창은 320px 고정 | **거의 무관.** 중심만 맞으면 됩니다 |
| **2단계 `m2.5`** | **크기.** 긴 변 × 2.5 | **배율이 통째로 달라집니다** |

실측으로 확인한 것 — 네모를 가로 +6%p, 세로 +10%p 헐렁하게 잡으면:

```
1단계 창  320px → 320px   (안 변함)
2단계 창  350px → 620px   (1.8배)
```

2단계는 이게 그대로 **배율 교란**입니다. 우리가 잰 convnextv2_base 의 배율 하락은
**holdout 20.5% / val 26.8%** (STEP 16) 이니, 네모를 헐렁하게 잡을수록 그쪽으로
갑니다. ⚠️ 여기 한동안 "18.4%" 라고 적혀 있었는데 그건 **STEP 12 서브셋** 값이라
낡았습니다.

→ **그래서 가이드 프레임은 고정 크기면 안 되고 끌고 늘릴 수 있어야 합니다.**
데모(`demo/index.html`)가 그렇게 되어 있습니다: 끌어서 옮기고 모서리로 크기를 바꾸며,
**중심을 고정한 채** 커집니다(모서리 기준으로 늘리면 크기를 맞추는 동안 가운데
정렬이 풀립니다 — 실제로 그렇게 나왔습니다). 네모는 항상 **원본 픽셀 기준 정사각**
입니다.

#### 밴드 밖이면 모델을 돌리기 전에 돌려보냅니다

네모가 있으면 촬영 가이드 밴드를 **추론 전에** 검사합니다(`agent.check_guide`).
그 구간에서 성능이 떨어지는 걸 이미 재 뒀는데(STEP 10), 넣고 나서 틀리는 것보다
안 넣는 편이 낫습니다.

```
권장 : 가로 28% ~ 48%      (하락 5% 이내)
허용 : 가로 24% ~ 56%      (하락 10% 이내)
위치 : 중앙에서 10% 이내
```

⚠️ **이 표는 며칠 동안 STEP 10 값(권장 34~56% / 허용 28~68%)이었습니다.**
밴드 출처를 `src/robust.py` 하나로 모으면서 `agent.py`·`box_error.py`·
`demo/index.html` 은 맞췄는데 **이 문서를 목록에서 빠뜨렸습니다.**
앱 팀은 코드가 아니라 이 문서를 보고 만듭니다 — 코드가 맞아도 문서가 틀리면
앱이 틀립니다. 이제 `tests/test_capture_guide.py::test_band_has_one_source`
가 **다섯 곳**을 한꺼번에 대조합니다.

밴드 밖이면 `verdict: "retake"` 에 `meta.retake_reason` 이 붙습니다
("조금 더 가까이에서 찍어주세요" 등) — 그대로 띄우면 됩니다.

#### 아직 남은 것

`box` 를 **안 주면** 화면 중앙으로 물러섭니다. 1단계는 중심만 쓰니 큰 차이가
없지만 2단계는 어긋납니다. 응답의 `meta.box_source` 가 `"user"` / `"center"` 로,
`meta.crop_note` 가 그때의 한계를 실어 나릅니다.

그리고 **네모의 분포가 다릅니다.** 라벨러는 답을 알고 병변에 딱 맞춰 그렸고,
사용자는 모르는 채로 대충 맞춥니다. 크롭 **구성**은 같아졌지만 이 차이는 남습니다.

#### 얼마나 정확히 그려야 하나 — 이미 재 뒀습니다

`robust.usable_range()` 가 STEP 16 에서 뽑은 배율 밴드를 **네모 오차로 뒤집으면**
그대로 앱의 사양이 됩니다. 네모를 r 배로 그리면 크롭이 r 배 넓어지므로 환산 줌은 1/r:

| | 배율 밴드 | ⇒ 네모 크기 오차 |
|---|---|---|
| 권장 (하락 5% 이내) | 0.7 ~ 1.2× | **0.83 ~ 1.43배** |
| 허용 (하락 10% 이내) | 0.6 ~ 1.4× | **0.71 ~ 1.67배** |

**1.5배로 그리면 아직 허용 안이지만 권장 밖입니다.** 중심은 2단계 크롭 폭의 10% 이내.

⚠️ **STEP 10 과 다릅니다** (권장 0.71~1.18 / 허용 0.59~1.43 이었습니다).
작게 그리는 쪽은 너그러워지고 **크게 그리는 쪽이 빡빡해졌습니다** — 2.0x 에서
macro-F1 이 0.449 입니다. 앱에 예전 숫자가 박혀 있으면 같이 고쳐야 합니다.

#### 사람이 실제로 얼마나 어긋나는지 재는 법

```bash

```

AI Hub 사진을 한 장씩 띄우고 네모를 맞추게 한 뒤 **정답 bbox 와 비교**합니다
(정답은 넘긴 뒤에 초록 점선으로 보여줍니다). 오차를 위 밴드에 대입해
"허용 안 몇 %" 까지 뽑습니다. 결과는 `reports/box_error.json`.

⚠️ **수의사가 필요 없습니다.** 수의사는 *병명*을 붙이는 사람인데 여기서 재는 건

⚠️ **여기 적혀 있던 "2단계 T=1.1063" 도 틀린 값**이었습니다 (실제 0.8890).

⚠️ **다만 "보정했다" 를 성과로 말하면 안 됩니다.** 두 단계 다 ECE 가 **조금

⚠️ **화면에 %를 띄울지는 여전히 열린 문제**입니다. 보정 여부와 별개로,

### ★ 3. `to_train_space` 가 **왜** 있어야 하는지 실측으로 확인됐습니다 (STEP 24)

`manifest_final.parquet` 365,428장이 사실상 전부 **1920×1080** 입니다
(청크 3개 모두 최빈 해상도 비중 100.0%). 학습·평가 내내
`rho(병변 절대 픽셀, 화면 점유율) = +1.000` — **두 값이 같은 변수**였습니다.

그래서 1단계 `f320`(절대 픽셀 창)의 "320" 은 **1920×1080 에서만** 뜻이 있습니다.
`agent.to_train_space()` 가 짧은 변을 1080 으로 맞추는 이유가 이것이고,
**이미 추론 경로에 들어가 있습니다** (`agent.py`, 크롭 **전에** 호출).
STEP 24 는 그 장치가 없으면 어떻게 되는지를 수치로 못 박은 셈입니다 —
4032×3024 사진을 그냥 넣으면 320px 창이 **절반 화각**을 봅니다.

**그래도 남는 한계 두 가지:**

1. **가로세로비가 다르면 완전히 같아지지 않습니다.** 학습은 16:9 인데 폰은 4:3 이
   흔합니다. 짧은 변을 맞춰도 가로 화각은 다릅니다. (짧은 변 기준이 맞는 선택인
   건 맞습니다 — 세로 화각이 병변 크기를 결정하니까요.)
2. **광학 줌·접사는 정규화로 못 되돌립니다.** 같은 1080 이어도 2배 줌으로 찍으면
   병변이 2배 큽니다. 이건 촬영 가이드 밴드가 잡아야 할 몫입니다 (§1 밴드 검사).

⚠️ **2단계는 지금 `m2.5`(비례 창)라 이 위험이 훨씬 작습니다. 그리고 그대로
갑니다** — STEP 22 가 고정 창(`f320`)을 후보로 올렸지만 **STEP 23 이 전체
데이터에서 기각**했습니다 (macro-F1 −0.0099, 배율 하락 +9.1%p).
⚠️ 여기 한동안 *"STEP 22·23 이 고정 창으로 바꾸자고 한다"* 고 적혀 있었는데
**반대**입니다.

살아남은 후보는 **크롭 뷰 앙상블**(`m2.5` + `f320` 모델의 확률 평균)이고,
그건 **비례 창을 버리지 않습니다** — 배율 하락이 23.5% → 24.4% 로 그대로입니다
(STEP 26). 즉 **채택해도 이 항목과 촬영 가이드 밴드는 안 바뀝니다.**

## 데모 화면 = 앱의 챗봇 카드

`demo/index.html` 은 **DAENGS 앱의 챗봇 화면을 그대로 옮긴 것**입니다
([`gayeoniee/isometric_test`](https://github.com/gayeoniee/isometric_test) —
`app/src/main/java/com/daengs/app/ui/home/ChatbotCard.kt`).

### 동선 — 들어오는 길이 둘입니다

```
챗봇 카드 ─ [📷 이미지 진단]
              ↓
          "찍을래, 아니면 가지고 있는 걸 올릴래?"
              │
    ┌─────────┴──────────┐
    │ 사진 찍기           │ 앨범에서 고르기
    │ 카메라에 네모를     │ 파일 선택 · 끌어놓기 · 붙여넣기
    │ 띄우고 그대로 촬영  │ (셋 다 같은 곳으로 갑니다)
    └─────────┬──────────┘
              ↓
          ★ 네모 맞추기 — 끌어서 옮기고 모서리로 크기 조절
            찍기로 왔으면 촬영 때 맞춘 네모가 **미리 채워져** 있습니다
            밴드 밖이면 "이 부위로 확인하기" 가 잠깁니다
              ↓
          내 말풍선에 사진이 뜸 (오른쪽, 핑크)
              ↓
          🐶 발자국 세 개가 통통 (타이핑 표시)
              ↓
          POST /v1/screen  (photo + box)
              ↓
          봇 말풍선에 결과 카드 — 이상 가능성 게이지 →
          "판단할 수 없어요" → 여섯 줄 분포 → 진료 권함 → 면책
```

**네모 맞추기 단계가 장식이 아닙니다.** 그 네모가 그대로 bbox 로 가고,
학습과 같은 크롭이 만들어집니다 (§1).

#### 두 길이 다른 이유

| | 찍기 | 올리기 |
|---|---|---|
| 네모를 언제 맞추나 | **찍기 전** — 프레임 안에 들어오게 찍음 | **찍은 뒤** — 이미 있는 사진 위에서 |
| 밴드 검사 | 셔터가 잠깁니다 | 확인 버튼이 잠깁니다 |
| 장점 | 구도부터 맞으니 다시 찍을 일이 적음 | 이미 찍어둔 사진, 다른 사람이 보낸 사진도 됨 |

찍기 쪽이 이상적이지만 **올리기가 없으면 안 됩니다** — 이미 찍어둔 사진,
가족이 보내준 사진, 병원 가기 전에 찍어둔 기록 사진이 다 그쪽입니다.

웹 데모는 `getUserMedia` 로 실제 카메라를 엽니다. 권한이 없거나 데스크톱이면
`<input capture="environment">` 로 물러섭니다 — **막히지 않고 항상 다음 단계로
갑니다.** 안드로이드에서는 CameraX 프리뷰 위에 같은 네모를 얹으면 됩니다.

박스 조작 코드는 **카메라와 첨부가 공유**합니다(`attachBox`). 두 곳에 따로 두면
갈라지고, 갈라지면 한쪽만 학습과 어긋납니다.

칩을 누르면 입력창에 채워지는 동작은 `ChatbotCard.kt` 와 같습니다.
**텍스트 대화는 아직 없습니다** — 보내면 "지금은 피부 사진만 볼 수 있어" 로
정직하게 답하고 이미지 진단으로 안내합니다.
