## 1. 확정된 스키마 ★

`diagnose.py` 로 실제 JSON 을 열어 확인한 내용입니다.
**추측으로 키를 박아두면 거의 확실히 틀립니다** — 실제로 세 군데가 틀렸고,
셋 다 에러 없이 그럴듯한 값을 만들어냈습니다.

| 필요한 것 | 실제 키 경로 | 형식 |
|---|---|---|
| **라벨** | `metaData.lesions` | `"A1"`~`"A6"`, `"A7"`=무증상 |
| 이미지 크기 | `metaData.resolution` | 문자열 `"1920X1080"` |
| 종 | `metaData.species` | `"D"`=개, `"C"`=고양이 |
| 합성 여부 | `metaData.합성유무` | `"Y"` / `"N"` |
| 병변 박스 | `labelingInfo[].box.location[0]` | `{x, y, width, height}` |
| 병변 폴리곤 | `labelingInfo[].polygon.location[0]` | **평평한 dict** `{x1,y1,x2,y2,…,xN,yN}` |
| 개체ID | ❌ **없음** | 대용 키를 만들어 씀 (아래 3절) |

### ⚠️ 실제로 당한 함정 3가지

**① 라벨을 폴더명에서 읽으면 안 됩니다.**
무증상 이미지가 `무증상/A1_구진_플라크/` 처럼 **병변 이름 폴더 안에** 들어 있습니다.
폴더명을 믿으면 무증상 23,669장이 병변 라벨을 받습니다.
= 모델에게 "정상 피부 = 병변" 을 가르치게 됩니다. 반드시 `metaData.lesions` 를 보세요.

**② 이미지 크기를 박스에서 읽으면 안 됩니다.**
박스의 `width`/`height`(예: 94×72)를 이미지 크기로 착각하면
병변 면적 비율이 **항상 정확히 100%** 로 나옵니다. 그럼 "ROI 크롭이 필요한가" 를
판단할 근거가 사라집니다. `metaData.resolution` 을 파싱하세요.
바로잡은 뒤 실제 값은 **0.33%** 수준이었습니다 (선행 보고 "93% 가 5% 미만" 과 일치).

**③ 폴리곤은 점 목록이 아닙니다.**
`[[x,y], [x,y], …]` 가 아니라 `{"x1":.., "y1":.., …, "x111":.., "y111":..}` 형태의
평평한 dict 입니다. 점 목록으로 가정하면 폴리곤 추출률이 **0%** 가 되는데
bbox 로 조용히 대체되므로 눈치채기 어렵습니다.

**④ 반려견 폴더에 고양이가 섞여 있습니다.**
예: `IMG_C_A7_026154.json`. 폴더로 필터하지 말고 `metaData.species == "D"` 로 거르세요.

## 3. 개체ID 가 없다는 문제와 대용 키

데이터에 개체(강아지) 식별자가 없습니다. `Raw data ID` 는 **이미지마다 고유**해서
그걸 개체ID 로 쓰면 "개체당 1.0장" 이 되고, 개체 단위 분할이 사실상
이미지 단위 분할로 퇴화합니다 — **누수 방지 장치가 무력화됩니다.**

대용 키:

```python
surrogate_animal_id = (species, breed, age, gender, date)
```

결과: 개체 **2,634마리**, 개체당 평균 **17.8장**.

| | 판단 |
|---|---|
| 서로 다른 개가 같은 그룹으로 묶일 수 있음 | ✅ 안전한 방향 (분할이 더 보수적) |
| 같은 개가 **다른 날** 재방문하면 다른 그룹으로 갈라짐 | ⚠️ **남는 위험** |

두 번째는 완전히 못 막습니다. 다만 `dedup.py` 의 phash 클러스터를
그룹에 union 하므로, 비슷한 사진끼리는 날짜가 달라도 같은 그룹으로 묶입니다.
그래도 "같은 개, 다른 날, 다른 부위" 는 갈라질 수 있습니다.
**개체 단위 분할에서 0.95+ 가 나오면 이 경로를 의심하세요.**

## 4. 전처리 결과 (VL01 실행 기준)

```
JSON 55,117 / 이미지 55,120
  ↓ 반려견(species=="D") + 일반카메라 필터
47,611행
  ↓ 라벨 없는 행 제외 (drop_unlabeled)
47,005행 전후          ← 'NA' 가짜 클래스가 fold 에 섞이는 것을 막습니다
  ↓ phash 중복 제거 (hash_size=16, hamming ≤ 6)
45,885행 / 그룹 2,605개 (개체 17.8장)
  ↓ 개체 단위 분할 (StratifiedGroupKFold 5-fold + holdout 15%)
train 31,476 / val 7,869 / holdout 7,138          ← 중복 제거 전 기준 수치
```

누수 점검 결과 (`split.verify(strict=True)`):

| 점검 항목 | 결과 |
|---|---|
| fold 간 그룹 중복 | **0** ✅ |
| holdout ↔ 개발용 그룹 중복 | **0** ✅ |
| train ↔ val 개체 중복 | **0** ✅ |
| train ↔ val phash 중복 | **0** ✅ |
| fold 별 클래스 비율 편차 | 0.1 pp 이내 ✅ |

## 5. 알려진 남은 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 개체ID 대용 키의 날짜 분리 | 누수 잔존 가능 | phash union + 0.95+ 결과 의심 |
| **ROI 크롭 전제** | 실사용 사진에는 병변 박스가 없음 | `full` 크롭 점수를 기대치로 사용 (아래) |
| VL01 한 청크만 사용 | 다양성 부족 | `--chunk TL01` 로 추가 가능 |
| 합성 이미지 포함 | 실사진 분포와 다름 | 원본과 같은 그룹으로 묶어 누수는 차단 |

### ROI 크롭 전제가 왜 중요한가

`m1.5` / `m2.5` 크롭은 **정답 박스를 알고 있다는 전제**로 잘라낸 이미지입니다.
실제 보호자가 찍은 사진에는 그 박스가 없습니다. 따라서

- `m1.5` / `m2.5` 점수 = 병변 위치를 아는 경우의 **상한선**
- `full` 점수 = 실제 서비스에 가까운 **정직한 숫자**

노트북 03 의 크롭 비교에서 두 값의 격차를 확인하세요.
격차가 크다면 배포 시 **병변 검출 모델을 앞에 붙이거나** `full` 로 학습해야 합니다.
