## 1. 크롭 비교 결과 (STEP 4C)

어제 만든 `03c_크롭비교` 를 풀 데이터·같은 실행에서 돌린 결과입니다.

| 크롭 | macro-F1 | 배율 하락 | A1 recall |
|---|---:|---:|---:|
| m1.5 | 0.5536 | 23.2% | 0.560 |
| **m2.5** | 0.5395 | **18.8%** | **0.622** |
| 차이 | −0.014 (잡음) | **−4.4%p** | **+0.063** |

**→ m2.5 채택.**

### ★ 오늘의 핵심 통찰

같은 목표(배율 견고성)를 두 방법으로 시도했는데 **방향이 정반대**였습니다.

| 방법 | 실제로 하는 일 | 결과 |
|---|---|---:|
| `zoom_both` 증강 | 자른 이미지를 **줄이고 여백으로 채움** → **정보를 버림** | +4.0%p 악화 |
| **m2.5 크롭** | **더 넓은 실제 영역**을 자름 → **정보를 더함** | **−4.4%p 개선** |

> 💡 **한 문장으로**: "작게 보이는 사진에 강해지려면,
> **작게 만들지 말고 넓게 찍은 걸 보여줘라.**"
>
> 증강은 원본을 축소해서 가짜 "멀리서 찍은 사진" 을 만듭니다 — 픽셀이 사라집니다.
> 넓은 크롭은 **실제로 존재하는 주변 픽셀**을 가져옵니다. 겉보기엔 같은데 완전히 다릅니다.

## 2. ⚠️ 제가 틀렸던 것 — 1단계는 크롭을 따라오지 않습니다

m2.5 를 확정하고 "그럼 1단계도 m2.5 로 맞추자" 고 커밋했습니다. **틀렸습니다.**

1단계는 **정상 / 이상**을 가리는 단계입니다. 여기서 ROI 크롭을 쓰면:

```
정상 사진 bbox 면적 중앙값 : 0.71%
병변 사진 bbox 면적 중앙값 : 1.25%
```

**크롭 창 크기가 정답을 흘립니다.** 사진을 아예 안 보고 창 크기만으로 맞히는
하한선(shortcut baseline)이 **AUROC 0.6042** 나옵니다. 랜덤이 0.5 니까 절반쯤 맞히는 겁니다.

**그리고 더 나쁜 건, 그 신호가 배포에 존재하지 않는다는 것입니다.**
보호자 사진에는 bbox 가 없으니까요. 검증 점수만 올리고 실사용에서 사라지는,
**최악의 지름길**입니다.

→ 1단계 크롭 우선순위: **`f320`(고정 픽셀) > `full` > ROI 크롭**.
현재 f320 이 없어서 **`full`** 을 씁니다.

### 이 실수에서 배운 것 (구조적)

규칙을 **노트북 셀**에 적어놨던 게 문제였습니다. 그래서 `src/crop.py` 로 옮겼습니다:

```python
crop.choose_stage1_tag(best_crop, scale_gap, full_ceiling, target_recall, tags)
# → {"tag": "full", "why": "...", "leaky": True, "warnings": [...]}
```

그리고 **실측 숫자를 테스트로 못 박았습니다** (7개). 제 e2e 테스트가 이걸 못 잡은
이유도 알았습니다 — 합성 픽스처에는 **배율 격차가 없어서** 규칙이 발동을 안 했습니다.
**테스트 데이터가 현실을 안 닮으면 테스트가 통과해도 의미가 없습니다.**

`CLAUDE.md` 에 "1단계 = m1.5" 라고 잘못 적혀 있던 것도 고쳤습니다.
(사실 코드는 처음부터 `full` 이었고, 문서만 틀렸던 겁니다.)

## 3. 전체 재기준선 (STEP 4D) — 2시간 18분

크롭을 확정했으니 **두 단계를 한 실행에서 다시** 쟀습니다. 지금부터의 비교 기준입니다.

| | 지표 | 값 | 목표 | |
|---|---|---:|---:|---|
| 1단계 | 정상·이상 AUROC | 0.8155 | 0.80 | ✅ |
| 2단계 | 병변 6종 macro-F1 | 0.5313 | 0.55~0.65 | ⚠️ 하단 미달 |
| 2단계 | A6(결절·종괴) recall | 0.340 | 0.50 | ❌ |
| 파이프라인 | 스크리닝 recall | 0.9501 | ≥0.95 | ✅ |
| 파이프라인 | 헛알림(false positive) | 51.4% | — | 감수 |
| 2단계 | 배율 교란 하락 | **16.0%** | <15% | ◐ 구분 불가 |
| 2단계 | 위치 교란 하락 | **16.2%** | <15% | ◐ 구분 불가 |

**위치 축이 같이 잡힌 건 예상 밖이었습니다** (20.6% → 16.2%).
사후 설명은 됩니다 — 넓게 자르면 병변이 화면 정중앙에만 있지 않으니
위치가 흔들려도 덜 민감해집니다. 다만 이건 **관찰에 맞춘 설명**이지 예측이 아니었습니다.

### ◐ "구분 불가" 라고 쓰는 이유

목표 15% 인데 실측 16.0%. 차이 1.0%p. 그런데 우리 **잡음 폭이 ±3%p** 입니다.
"목표 미달" 이라고 쓰면 없는 정밀도를 있는 척하는 것이고,
"달성" 이라고 쓰면 반대로 과장입니다. **◐ 구분 불가**가 정확합니다.

> 💡 이게 이 프로젝트의 규칙 1번("숫자는 실측만")의 실전 적용입니다.
> **잡음보다 작은 차이로 결론을 내리지 않습니다.**

### 그리고 제 이전 주장을 정정했습니다

STEP 4C 에서 "m2.5 의 macro-F1 손해는 잡음이고 사실상 대가가 없다" 고 썼는데,
측정이 하나 더 쌓이니 그림이 달라졌습니다:

| 크롭 | 측정 1 | 측정 2 | 평균 |
|---|---:|---:|---:|
| m1.5 | 0.5697 | 0.5536 | 0.562 |
| m2.5 | 0.5395 | 0.5313 | 0.535 |

**네 번 다 m1.5 가 위입니다.** 개별 차이는 신뢰구간 안이지만 방향이 일관되므로,
"대가 없음" 이 아니라 **"작지만 아마 실재하는 대가(−0.027쯤)"** 로 표현을 낮췄습니다.
견고성 이득(−9.9%p)이 잡음의 3배라 **m2.5 는 유지**합니다.

## 4. 노트북 인계 지옥 — 오늘 하루의 절반

Kaggle 은 **노트북마다 세션이 따로**입니다. 03 이 3시간 걸려 만든 체크포인트는
05 를 열면 **없습니다.** 여기서 연달아 막혔습니다:

| # | 증상 | 원인 | 고친 것 |
|---|---|---|---|
| 1 | 05 가 체크포인트를 못 찾음 | 세션이 다름 | `import_checkpoints()` 자동 탐색 |
| 2 | 가중치는 왔는데 임계값 JSON 이 없음 | 가중치만 인계 | `import_previous_run()` + 임계값 재계산 |
| 3 | 낡은 실행(m1.5)을 붙임 | 검증이 없음 | `ADOPTED_STAGE2_CROP` 불일치 시 정지 |
| 4 | 크롭이 0%라고 나옴 | **빈 폴더**가 진짜 데이터셋을 가림 | 빈 태그 폴더 건너뛰기 |

4번이 재밌습니다. 데이터셋 이름 `03notebook` 이 `dogskin-m25` 보다 **알파벳 순으로
앞서서**, 그 안의 **비어 있는** `crops/m2.5` 폴더가 먼저 링크됐습니다.

그리고 근본 원인이 드러났습니다: **노트북 하나를 돌려쓰고 있었습니다.**
03 을 지우고 05 를 붙여넣으면, 05 에 붙일 03 이 **없어집니다** (자기 자신은 입력이 안 됨).

→ **`03` / `03b` / `03c` / `05` 를 각각 별도 노트북으로.**
→ 인계를 **`release` 꾸러미 하나**로 정리했습니다:

```
release/
├── READ_ME_FIRST.txt      ← 이 실행이 뭐였는지 사람이 읽을 요약
├── checkpoints/<exp>/best.pt
├── stage1_threshold.json
└── release.zip            ← Kaggle 은 폴더 하나만 내보내기가 안 돼서
```

`notebooks/README.md` 도 새로 썼습니다 (어떤 노트북을 언제·무엇을 붙여서 돌리나).
